# ADR 0036: A showcase web app, with a development-only device that runs in the browser

**Status:** Proposed · **Priority:** Should · **Date:** 2026-10-27

**In one line:** A small, server-rendered web app lets anyone see every stage of the system working in a browser: instruments rendered and evaluated, the publishing log verified, registration, a collection device, the upload and the intake. The device is the real format core compiled to WebAssembly, on a new development-only `web` platform profile. It is an unattested software device and deployment validation refuses it in production.

*The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals.*

## Context

Until now the only way to look at an instrument was `fieldseal instrument preview`, which writes one static page. There was no way to watch the whole system run without an Android device or reading CLI output. The people who own the product need to assess whether the system and its tools are built to the specification, and a browser is the one client everyone already has.

## Decision

1. **Purpose.** The web app is a development and assessment showcase. It is **not** a production client and does not replace the Android runtime. It calls the real contexts and adapters; nothing it shows is faked, and where something is simulated (an authority, a key store) the page says so.
2. **Place in the hexagon.** The server (`crates/apps/web`) is an outer app (ADR 0028). It composes contexts and adapters, serves server-rendered HTML with a small hand-written script, and adds no framework. The browser side is a binding (`crates/bindings/wasm`, wasm-bindgen) over a new adapter crate (`crates/adapters/web`) that holds the `web` profile's ports and the instrument workbench. The contexts stay pure; everything browser-specific (IndexedDB, the clock, the HTTP call) sits behind ports. An embedded **demo authority** (`crates/adapters/web-demo`) lets the app work with no other service; it is the in-memory practice authority the simulator and tests already use, wired to the real factory and upload HTTP adapters.
3. **A `web` platform profile** (PLAT-100 and following), development only. It meets the platform ports in software and declares what a tab cannot do as `unmet`: no hardware key storage, no operating-system secure display, no device lock-down. PLAT-045 would refuse a session when an invariant is unmet; the web profile is allowed to run only because it is refused anywhere that matters (point 5), and every screen states that the device is unattested.
4. **Why the device runs in the browser.** The user wanted to exercise the whole path from a browser and judge it against the spec. Compiling the same Rust core gives parity for free: the same bundle verification in WIRE-093 order, the same render plan, rules and field checks, the same HPKE-sealed dual write, export and receipt checks. Re-implementing any of it in JavaScript would test a copy, not the system. The device runs in a dedicated worker because the contexts' ports are synchronous and uploads need a blocking HTTP call (allowed in workers); the page is a thin user interface.
5. **Custody, with honest limits.**
   - Keys are generated by the core in WebAssembly from the browser's CSPRNG (`crypto.getRandomValues`). WebCrypto cannot be used for them directly: its API is asynchronous and cannot perform the core's HPKE, so it cannot sit behind the synchronous key-store port. WebCrypto is used where it fits: the host script wraps the key material with a non-extractable AES-GCM `CryptoKey` kept in IndexedDB.
   - Keys and the sealed journal are kept in IndexedDB, through a write-through log that the host persists after every call.
   - While the page is open the keys are in the worker's memory. Any script in the page's origin could reach them. This is a software key store, not a hardware boundary.
   - The device is **unattested** (CLI-007, REG-017): its requests carry `software` evidence, which production policy refuses (TRU-061).
   - The PIN is hashed with the real Argon2id (64 MiB, 3 passes), so unlocking takes a moment.
6. **Production refusal.** The `web` adapter name is a development adapter in deployment validation (DEP-023, like `memory` and `software`), and the server refuses `FIELDSEAL_ENVIRONMENT=production` (WEB-190).
7. **The device is never reported as attested.** The release policy denies rosters to unattested keys (INV-10). For the showcase, the demo factory runs with the existing non-production allowance for unattested keys (REG-017, CLI-007): the development policy releases rosters to the software device with a flag in the decision log. The device's attestation facts are never invented or altered (TRU-061, TRU-063): it is unattested in the registry, in its evidence and on every screen ("unattested software device, development policy allows it"). Production refuses the allowance and the `web` adapter.
8. **Hick's Law and the Android design system.** The interface follows Hick's Law ([lawsofux.com/hicks-law](https://lawsofux.com/hicks-law/)): few choices at once, tasks broken into steps, one primary action per screen, progressive disclosure, a highlighted default. The spec makes it testable: at most five top-level destinations, exactly one `btn-primary` per screen, secondary content behind `<details>` or tabs, one step at a time on the device following the layout's grouping and the choice-load thresholds INS-210 and INS-211 (WEB-180 to WEB-185). Visually it reproduces the Android app's design system (white ground, deep green, Nunito Sans bundled locally, 72 px header with step pills, rounded cards, pill buttons, 52 px targets) rather than a generic look; the instrument's own look is the HTML adapter's theme and changes no instrument or layout semantics (ADR 0033).
9. **Constraints are enforced where they are shown.** A hint such as "choose up to 4" or "between 1 and 20" is not enough: the page refuses what breaks the declared constraint (typed input included), the core's problem is shown, and the device cannot hold or seal a value that breaks it (WEB-186).

## Consequences

- The system can be judged from a browser with `nix run path:.#fieldseal-web`, with only `examples/`.
- The WebAssembly build adds a Nix derivation, a pinned `wasm-bindgen-cli` (its version must equal the crate's) and a `wasm32-unknown-unknown` target. The core must stay free of 64-bit assumptions: the software attestation checksum used `usize` and differed on a 32-bit target until it was fixed in the adapter.
- A browser tab is not a field device: no secure display, no lock-down, and the user can clear site data. The profile's limits are in the spec and shown in the UI.
- A browser download cannot be read back through its destination; Delivery's read-back verifies the bytes handed to the browser.

## Alternatives rejected

- **A JavaScript device.** Rejected: it would test a re-implementation.
- **An Android emulator in the browser.** Rejected: far heavier and no clearer.
- **A server-side simulated device with a web front end.** Rejected: the user wants the collection device itself, in the browser, with keys that never reach the server.
